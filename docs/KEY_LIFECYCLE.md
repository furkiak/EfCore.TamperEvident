# HMAC key lifecycle and old-chain verification

The preview requires base64 encoding of at least 32 randomly generated bytes. Registration rejects missing, malformed, short and uniform keys. This validation cannot prove how a caller generated its key. Generate it with a cryptographic RNG once, store it in a secret manager, and never include it in source, a package, email, logs or screenshots.

For an ASP.NET development application, enable user secrets on that application's project, then set `Audit:HmacKey` through the application's secret-manager tooling. `builder.Configuration["Audit:HmacKey"]` in the README reads that provider alongside the other configured providers. Use the host's protected secret manager for a deployed application. The library has no built-in cloud secret-manager client and must receive the resolved value from its host.

## Operational key identity

Maintain an access-controlled registry outside the audited database: deployment/chain identifier, key identifier, provider secret-version reference, activation time, audited database/table identities, hash-format version, and independently retained anchor references. Store the key itself only in the secret manager. The current v2 rows do **not** contain a key ID and the verifier accepts one key; an operational key ID is not a supported per-row rotation mechanism.

## Rotation without invalidating retained evidence

1. Stop audited writers and the dispatcher; record an independently retained final anchor and verify the old chain with the original key.
2. Preserve the old database snapshot, original key version, original verifier/application version and external anchor ordering. Restrict those materials to the verification role.
3. Provision a new isolated audit database/chain with a fresh random key and a new deployment/chain identifier. Review its schema and access boundaries. Do not switch keys halfway through the existing v2 chain.
4. Retain a signed or independently protected handover record that identifies the old terminal anchor and the new chain. This handover is an operational evidence record, not an automatic feature of the library.
5. Verify old data using its original key and matching format; verify new data using the new key. Remove the old key from active writers while retaining it in the restricted historical-verification store.

If a key was exposed, treat evidence created under it as potentially forgeable. External anchors retained before exposure can establish a limited comparison point; rotation does not retroactively prove unanchored history. Investigate the compromise and its time bounds separately.

## 1.x to v2

NuGet 1.0.1 and the v2 preview use different configuration, schema and hash inputs. The v2 verifier rejects v1 hashes. Preserve the 1.x database, its original key and externally retained anchors; verify it with the matching historical code/package in an isolated read-only environment. There is no in-place migration tool in this preview. Start a separate v2 chain only after the handover has been reviewed. Never rehash, delete or reset old rows merely to make a v2 verification pass.
